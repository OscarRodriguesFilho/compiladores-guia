04 a teoria vira código

Diagrama sintático, tokenização e o embrião do Parser
A frase que separa as duas fases — e que vale para o semestre inteiro

O Lexer decide "que token é este?". O Parser decide "essa sequência de tokens é válida?". Duas perguntas completamente diferentes, e é por isso que são duas classes.

1

A linguagem de partida

Uma calculadora mínima: só + e -, com números de vários dígitos. São válidas:

1
1+1
1+2+3
11-22-33

A gramática que descreve isso cabe numa linha:

EXPRESSION → NUMBER { ( "+" | "-" ) NUMBER }

E a pergunta da aula é: como transformar essa regra em algo fácil de implementar?

2

O diagrama sintático

É uma terceira forma de representar a mesma gramática — e a mais próxima do código que virá depois. Em vez de símbolos, um trilho: você entra pela esquerda, percorre os caminhos possíveis e sai pela direita. Toda rota completa é uma cadeia válida.

Por que desenhar, se a EBNF já dizia a mesma coisa

Porque o diagrama já tem o formato do código. O trilho principal vira a sequência de instruções; o laço vira um while; a bifurcação entre + e - vira um if. Você não "traduz" a gramática: você copia o desenho.

3

Primeira responsabilidade: o Lexer

O Lexer recebe caracteres e devolve tokens — os "átomos" do código-fonte. Ele agrupa 1 e 2 num único INT(12), descarta espaços, e não tem opinião nenhuma sobre ordem.

4

Segunda responsabilidade: o Parser

O Parser não vê caracteres. Ele recebe a sequência de tokens e faz uma única pergunta: essa ordem obedece à gramática?

5

O detalhe do run(): conferir o EOF

O run() recebe o código, cria o Lexer, posiciona no primeiro token, chama parse_expression() e — este é o ponto — confere se o próximo token é EOF.

Sem essa checagem, 1+2 3 passaria

O Parser reconheceria 1+2 perfeitamente, chegaria à saída do diagrama e devolveria 3 — deixando o 3 final para trás, sem reclamar. A checagem de EOF é o que garante que toda a entrada foi consumida, e não apenas um pedaço válido dela. Selecione o exemplo 1+2 3 acima para ver onde ele morre.

def run(code):
    Parser.lexer = Lexer(code)
    Parser.lexer.select_next()           # posiciona no primeiro token
    result = Parser.parse_expression()

    if Parser.lexer.next.type != "EOF":   # ← sem isto, "1+2 3" passaria
        raise Exception(...)

    return result

05 fecha o bloco de linguagens regulares

Expressões regulares, AFD/AFN, pumping e fechamento
O que esta aula fecha

Ela amarra tudo que se pode dizer sobre linguagens regulares — três formas equivalentes de descrevê-las, uma ferramenta para provar que algo não é regular, e as operações que preservam a classe. É a última aula antes de a linguagem do compilador precisar de mais poder.

1

O exemplo que motiva: validar e-mail

A aula parte de um problema concreto: descrever o formato de um endereço de e-mail. É o caso perfeito porque um e-mail tem estrutura, mas não tem aninhamento — e é exatamente essa a fronteira das linguagens regulares.

2

Três formas de dizer a mesma coisa

Uma linguagem regular pode ser descrita de três jeitos, e os três têm exatamente o mesmo poder. Para L = { abn : n ≥ 0 }:

3

AFD e AFN têm o mesmo poder

AFD — determinísticoum caminho só

Para cada par (estado, símbolo) existe uma única transição. Dado o estado atual e o caractere lido, não há escolha a fazer.

É o que o seu select_next() é.

AFN — não determinísticovários caminhos

Pode haver várias transições possíveis para o mesmo par. A palavra é aceita se algum caminho aceitar.

Converter uma gramática linear direto para autômato costuma produzir um AFN.

O AFN não é mais poderoso — só mais confortável

Esse é o ponto contraintuitivo da aula: AFD e AFN reconhecem exatamente as mesmas linguagens, as regulares. Todo AFN pode ser convertido num AFD equivalente (ao custo de possivelmente muitos mais estados). O não determinismo é uma conveniência de projeto, não um ganho de expressividade.

4

Pumping lemma: provando que algo NÃO é regular

A intuição em uma frase: se uma linguagem regular tem palavras arbitrariamente longas, o autômato que a reconhece precisa repetir algum estado — ele tem um número finito de estados e a palavra não tem limite. Todo estado repetido é um ciclo, e ciclo pode ser percorrido quantas vezes você quiser.

L regular  ⇒  ∃ p  tal que toda w ∈ L com |w| ≥ p se escreve  w = x y z  com:

    |xy| ≤ p        (o ciclo acontece cedo)
    |y| > 0          (o ciclo consome pelo menos um símbolo)
    x yi z ∈ L       para todo i ≥ 0

O uso é sempre por contradição. Para L = { anbn }: suponha regular, pegue o p garantido, escolha w = apbp. Como |xy| ≤ p, o trecho y só contém a. Bombeando com i = 2 você ganha a sem ganhar b — a igualdade quebra. Contradição.

w = xyz — a divisão obrigatória pelo lema
x yi z — a palavra bombeada
5

Fechamento: operações que preservam a classe

Dizer que uma classe é fechada sob uma operação significa: se você começa com linguagens da classe e aplica a operação, o resultado continua na classe. As regulares são generosas nesse quesito — fecham sob praticamente tudo.

Isso não é curiosidade: é ferramenta de prova. Se L ∩ R não for regular e R for regular, então L não podia ser regular — senão a interseção seria. O detalhamento completo, comparando com as livres de contexto, está na Parte II, aba Fechamento.

Precedência: EXPRESSION, TERM, FACTOR
Se você guardar só uma ideia da aula, guarde esta

A precedência não é colocada na marra. Ela aparece porque a gramática é organizada em níveis, e os níveis mais internos terminam antes dos externos. Não existe tabela de prioridades em lugar nenhum do código.

1

Um nível por tipo de construção

EXPRESSION = TERM,   { ("+" | "-"), TERM }   ;
TERM       = FACTOR, { ("*" | "/"), FACTOR } ;
FACTOR     = ("+" | "-"), FACTOR | "(", EXPRESSION, ")" | NUMBER ;
nívelcuida deliga
EXPRESSION+ e -menos forte
TERM* e /médio
FACTORnúmero, unário, parêntesesmais forte

A primeira regra lê-se assim: uma expressão começa com um TERM e pode ser seguida por zero ou mais blocos do tipo + TERM ou - TERM. A segunda faz o mesmo para multiplicação e divisão.

2

Por que 3+4*2 vira 3+(4*2)

Porque parse_expression() chama parse_term(), que chama parse_factor(). O TERM termina de resolver 4*2 antes de devolver esse resultado para o EXPRESSION. Acompanhe o vaivém:

↓

  T  vê + e termina    # + não é dele, devolve 3
↑

Repare na linha "T vê + e termina": o + não pertence àquele nível, então o TERM devolve o que tem e deixa o + para quem o chamou. Esse deixar para o de cima é o mecanismo inteiro da precedência.

O depurador da aba v1.1, na Parte III, mostra esses quadros de chamada empilhando e desempilhando de verdade, cada um com o seu próprio result.

3

Operadores unários

Em -3, o - não é subtração entre dois operandos: ele se aplica diretamente ao 3. Por isso a gramática permite FACTOR → "-" FACTOR e FACTOR → "+" FACTOR.

E como FACTOR chama outro FACTOR, construções como --3, +-3 e +--++3 funcionam sem nenhum código específico para unários encadeados. É recursão fazendo o trabalho.

07 a linguagem sobe de classe

Gramáticas livres de contexto e autômatos de pilha
A motivação vem direto da Aula 6

Assim que o compilador passou a aceitar parênteses aninhados — (a), ((a)), (((a))) — a linguagem deixou de ser regular. Um autômato finito não tem como controlar quantos parênteses foram abertos e ainda precisam fechar.

1

Gramática livre de contexto

A definição formal continua a mesma quádrupla:

G = ( V , Σ , P , A )

    V   vocabulário           P   produções
    Σ   terminais             A   símbolo inicial

A novidade está na forma das regras:

α → β        com  α ∈ N  (um único NÃO TERMINAL)
                    β ∈ V*  (qualquer combinação de terminais e não terminais)

Em português: o lado esquerdo é sempre um não terminal sozinho — daí "livre de contexto": não importa o que está em volta, a regra pode ser aplicada. O lado direito, porém, é livre.

A gramática do aninhamento:

A → ( A )
A → a

gera:  a  ·  (a)  ·  ((a))  ·  (((a)))  …

Ela não é regular, porque A → (A) tem um terminal de cada lado do não terminal. Uma gramática linear só admite o não terminal numa ponta.

2

Por que um AF não basta

A aula tenta montar um autômato finito para essa linguagem. O resultado aceita os casos certos — e também aceita lixo:

deveria aceitare aceita

(a))

O diagnóstico: o autômato não tem memória para casar aberturas com fechamentos numa quantidade arbitrária. Ele sabe que leu um parêntese; não sabe quantos.

4

Aceitação por pilha vazia

O PDA que a aula constrói usa um critério de aceitação diferente do habitual: não há estado final. A palavra é aceita quando a entrada terminou e a pilha está vazia. Isso parece um detalhe técnico, mas é o que torna a equivalência do próximo passo elegante de provar.

5

O resultado central: GLC ↔ PDA

O teorema vale nos dois sentidos:

GLC → PDA

Dada uma gramática livre de contexto G, dá para construir um autômato de pilha não determinístico com aceitação por pilha vazia que reconhece exatamente L(G).

PDA → GLC

E o inverso: dado um PDA com aceitação por pilha vazia, dá para construir uma GLC equivalente.

É o mesmo tipo de correspondência que você já tinha visto um nível abaixo:

classegramáticareconhecedor

Livre de contextoGLCautômato de pilha
Cuidado: a equivalência é com PDA NÃO determinístico

Nem toda linguagem livre de contexto pode ser reconhecida por um PDA determinístico. Então não vale pensar "CFL = PDA determinístico". As linguagens que têm PDA determinístico formam uma subclasse própria — e não é coincidência que seja mais ou menos onde vivem as linguagens de programação, que precisam ser analisadas rápido e sem ambiguidade. A Aula 9 volta a esse ponto com LR(k).

08 prepara o Roteiro 4

Árvores de derivação, ambiguidade e AST
A frase que resume a aula inteira

Na Aula 6, o Parser já sabia calcular a expressão enquanto lia. Na Aula 8, ele passa a construir uma árvore que representa a expressão — e quem calcula é a árvore, depois. Todo o resto da aula existe para justificar essa troca.

1

Primeiro: o que é uma derivação

Uma derivação é o passo a passo de como a gramática gera uma cadeia. Você começa no símbolo inicial e vai trocando não-terminais pelas suas regras, até sobrar só texto. Para ver a ideia limpa, a aula usa a menor gramática interessante que existe:

S → a S b  |  ε        # ε (épsilon) = a palavra vazia

Ela gera ab, aabb, aaabbb… sempre a mesma quantidade de a e de b — o mesmo padrão dos parênteses da Aula 7, e pelo mesmo motivo não é regular.

Avance os passos e veja a derivação e a árvore crescerem juntas. A árvore é só a derivação desenhada: cada substituição vira um nó com seus filhos.

2

O problema: ambiguidade

Uma gramática é ambígua quando uma mesma cadeia admite duas árvores de derivação diferentes. Parece detalhe teórico. Não é: significa que o mesmo programa pode ter dois significados. Considere a gramática ingênua que qualquer um escreveria primeiro:

E → E "+" E  |  E "*" E  |  number

Ela aceita 3+4*2. O problema é como — de duas formas, ambas válidas segundo as regras:

Árvore 1 → 3+(4*2)o * agarra primeiro
= 11
Árvore 2 → (3+4)*2o + agarra primeiro
= 14
Mesma entrada, duas respostas

11 ou 14. Nada na gramática decide qual. Um compilador com essa gramática produziria resultados dependentes de um detalhe de implementação — qual regra o parser tenta primeiro. A linguagem deixaria de ter significado definido.

3

A solução: estratificar a gramática

É aqui que EXPRESSION, TERM e FACTOR deixam de parecer burocracia. Eles não foram inventados para organizar o código — foram inventados para eliminar a ambiguidade. Um TERM nunca pode conter um + solto; para isso teria que descer até FACTOR e entrar num parêntese. Então a Árvore 2 acima simplesmente não é derivável. Sobra uma, e só uma.

4

Um caso clássico: o dangling else

Ambiguidade não é problema só de contas. O exemplo mais famoso em linguagens de programação é o else pendurado:

if (a == b)
    if (c <= n)
        d++;
else
    d--;

Esse else pertence a qual if? A indentação sugere o primeiro, mas indentação não é gramática:

Leitura A — o else é do if de DENTRO
if (a == b) {
    if (c <= n)
        d++;
    else
        d--;
}
Leitura B — o else é do if de FORA
if (a == b) {
    if (c <= n)
        d++;
}
else
    d--;

Com a == b verdadeiro e c <= n falso, a Leitura A executa d-- e a Leitura B não executa nada. Comportamentos diferentes, mesmo texto.

Como as linguagens reais resolvem

C, Java, C# e companhia adotam a regra "o else pertence ao if mais próximo ainda sem else" — ou seja, a Leitura A. É uma decisão imposta por fora da gramática, que continua ambígua no papel. Python resolve de raiz: a indentação é sintaxe, então a pergunta nem chega a existir.

5

Da árvore de derivação para a AST

Resolvida a ambiguidade, sobra uma árvore — mas ela é grande demais. Para chegar ao número 3 em 3+4*2, a árvore de derivação desce por EXPRESSION → TERM → FACTOR → NUMBER, mesmo não havendo multiplicação nenhuma naquele ramo.

Esses nós cumpriram o papel deles — provar que a cadeia obedece à gramática — e depois disso não servem para mais nada. A AST é o que sobra quando você joga fora o andaime. Por isso ela é abstrata: o operador, que na derivação era um terminal consumido de passagem, vira o nó; e os não-terminais, que eram nós, desaparecem.

Na Parte II, aba Árvores, há um gerador que desenha as duas lado a lado para a expressão que você digitar.

6

Como a AST é executada

A avaliação é recursiva: cada nó resolve a própria operação, mas só depois de pedir aos filhos que resolvam a parte deles. Acompanhe a conversa para 3+4*2:

+Preciso somar. Quanto vale meu filho esquerdo?
3Sou uma folha, não tenho filhos: valho 3.
+E o meu filho direito?
*Espera — também preciso perguntar aos meus. Filho esquerdo?
4Valho 4.
*Filho direito?
2Valho 2.
*Então 4 × 2 = 8. Toma, +.
+Recebi 3 e 8. Logo, 3 + 8 = 11. Esse é o resultado final.

Três coisas para guardar dessa conversa. A execução vai de baixo para cima — a raiz é a última a produzir um valor, e é o valor final. Nenhum nó sabe quem é o seu pai. E o + não faz ideia de que o filho direito é uma multiplicação: ele pede um número e recebe um número. É exatamente isso que o depurador da aba v1.2 anima nó a nó.

09 estratégias de parsing e limites formais

LL, LR, e até onde as linguagens vão
A aula tem duas metades que não parecem conversar — mas conversam

A primeira é prática: LL(k) e LR(k) são duas estratégias para escrever um parser. A segunda é teórica: o pumping lemma para CFL, as propriedades de fechamento e a hierarquia de Chomsky dizem até onde cada classe alcança. O fio que liga as duas: as estratégias de parsing existem porque certas classes de gramática são tratáveis e outras não.

1

LL(k): analisar de cima para baixo

Um parser LL parte do símbolo inicial e vai expandindo regras até chegar na cadeia. As três letras significam:

siglasignificana prática
LLeft to rightos tokens são lidos da esquerda para a direita
LLeftmost derivationexpande sempre o não-terminal mais à esquerda
klookaheadquantos tokens precisa espiar para escolher a produção

O exemplo do material:

A → a A b  |  c              L = { am c bm : m ≥ 0 }

Essa gramática é LL(1): olhando um único token, a decisão já está tomada. Se o próximo for a, use A → aAb. Se for c, use A → c. Nunca há dúvida.

O seu compilador é um parser LL(1) — escrito à mão

Olhe o parse_factor(): ele consulta Parser.lexer.next.type — exatamente um token — e decide entre três alternativas (número, unário, parêntese). Isso é literalmente a definição de LL(1). O nome técnico do que você escreveu é descida recursiva (recursive descent): uma função por não-terminal, um token de lookahead. E é por isso que o atributo se chama next — ele é o lookahead.

2

LR(k): analisar de baixo para cima

Um parser LR faz o caminho inverso: parte da cadeia e vai reduzindo pedaços até sobrar o símbolo inicial. Ele trabalha com uma pilha e duas operações:

shiftempilhar

Tira o próximo token da entrada e empurra na pilha. É o "ainda não sei o que isso vai virar, guarda aí".

O lema do bombeamento

O lema do bombeamento (pumping lemma) é uma ferramenta para provar que uma linguagem NÃO é regular — ou seja, que nenhum autômato finito consegue reconhecê-la, por mais estados que você lhe dê.

Ele importa muito concretamente aqui: é a razão formal de o FACTOR precisar chamar a si mesmo.

O enunciado

Se L é regular, existe um número p (o comprimento de bombeamento) tal que toda palavra w ∈ L com |w| ≥ p pode ser escrita como w = xyz, satisfazendo:
  (1) |xy| ≤ p   (2) |y| ≥ 1   (3) xyiz ∈ L para todo i ≥ 0

A intuição é simples: um autômato com p estados que lê uma palavra de p ou mais símbolos precisa repetir algum estado — não há estados suficientes para todos serem distintos. O trecho lido entre as duas visitas ao mesmo estado forma um laço. E um laço pode ser percorrido quantas vezes você quiser: zero, uma, mil. Se a linguagem é regular, todas essas repetições continuam válidas.

Então, para provar que algo não é regular, basta achar uma palavra que quebra ao ser bombeada.

Aplicando: parênteses balanceados não são regulares

Considere L = { (n )n : n ≥ 1 } — a linguagem dos parênteses que abrem e fecham na mesma quantidade. Suponha, por absurdo, que seja regular. Então existe p, e tomamos w = (p)p.

Pela condição (1), xy cabe nos primeiros p símbolos — que são todos abre-parênteses. Logo y só contém (. Bombeando com i = 2, a palavra ganha parênteses abertos a mais e nenhum fechado. O balanço quebra. Contradição — a linguagem não é regular.

Mexa nos controles e veja a contradição acontecer:

w = xyz (a divisão obrigatória pelo lema)
xyiz (a palavra bombeada)

x · y · z — o y só pode conter abre-parênteses, porque pela condição (1) ele tem que caber nos primeiros p símbolos.

A consequência direta no seu código

Se parênteses balanceados não são regulares, nenhum autômato finito os reconhece — portanto o Lexer jamais poderia ser encarregado disso. É preciso uma máquina mais forte: um autômato de pilha, que empilha ao abrir e desempilha ao fechar. E é exatamente isso que o Parser é. Ele nunca declara uma pilha — ele usa a pilha de chamadas do próprio Python, via a recursão do parse_factor(). Cada parêntese aberto é um quadro de chamada a mais.

A versão para linguagens livres de contexto

O mesmo raciocínio sobe um andar. Se uma CFL tem palavras arbitrariamente longas, a árvore de derivação de uma palavra suficientemente comprida precisa ser alta — e numa árvore alta, algum não-terminal reaparece no mesmo caminho, porque a gramática tem um número finito deles.

A diferença que importa: duas partes bombeadas, não uma

No caso regular, a palavra quebra em três partes e você repete uma: w = xyz, bombeia o y. Nas CFL, quebra em cinco e você repete duas ao mesmo tempo: z = uvwxy, bombeia v e x juntos. E isso não é uma escolha: é consequência de a recursão numa árvore crescer para os dois lados do não-terminal repetido.

O exemplo clássico: anbncn não é livre de contexto

A pilha de um PDA consegue casar duas quantidades — abre e fecha, a e b. Casar três ao mesmo tempo é demais para ela, e o pumping lemma prova isso.

Suponha CFL, pegue o n garantido e escolha z = anbncn. Como |vwx| ≤ n, o trecho vwx é curto demais para tocar as três letras — ele cobre no máximo duas delas (a e b, ou b e c). Bombeando com i = 2, as letras tocadas crescem e a terceira fica para trás. As três quantidades deixam de ser iguais. Contradição.

Por que isso importa para um compilador

anbncn parece artificial, mas tem análogo real: "toda variável usada foi declarada antes, com o tipo certo" é uma restrição desse tipo. É por isso que nenhuma gramática livre de contexto valida um programa por completo, e por que existe uma fase semântica separada — com tabela de símbolos — depois da sintática. A sintaxe cuida da forma; ela literalmente não alcança o resto.

O contraexemplo que prova que CFL não fecha sob interseção

Tome estas duas, ambas livres de contexto:

Cada uma casa um par de quantidades e deixa a terceira livre — uma pilha dá conta disso. Mas a interseção exige que os três casem ao mesmo tempo:

L₁ ∩ L₂ = { an bn cn }

E essa, pelo pumping lemma para CFL (aba anterior), não é livre de contexto. Duas CFL cuja interseção não é CFL: a classe não é fechada sob interseção.

Por que "interseção com regular" ser fechada é tão útil

É o truque padrão nas provas. Para mostrar que uma linguagem L não é livre de contexto, você a intersecta com uma linguagem regular escolhida a dedo, obtendo algo reconhecidamente não-CFL. Como CFL é fechada sob interseção com regular, se L fosse CFL o resultado também seria — contradição. A regular funciona como um filtro que isola a parte difícil.

Como usar isso numa prova

# Para provar que L NÃO é regular usando fechamento:

1. suponha que L é regular
2. escolha uma linguagem R comprovadamente regular
3. como regulares fecham sob ∩, então L ∩ R seria regular
4. mostre (por pumping) que L ∩ R NÃO é regular
5. contradição ⇒ L não era regular

A vantagem sobre aplicar pumping direto em L: às vezes L é bagunçada demais para escolher uma palavra boa, mas L ∩ R fica limpinha.

Duas árvores diferentes

A palavra "árvore" é usada para duas coisas distintas, e confundi-las atrapalha. A árvore de derivação registra cada regra da gramática que foi aplicada. A AST guarda só o que é necessário para calcular. Compare as duas para a mesma expressão:

A árvore de derivação é alta e repetitiva: para chegar ao número 2, é preciso descer por EXPRESSION → TERM → FACTOR → NUMBER, mesmo que nenhuma multiplicação exista ali. Esses nós intermediários provam que a string obedece à gramática — e depois disso não servem para mais nada.

Por que parênteses somem na AST

Experimente (2+3)*4 acima. Na árvore de derivação os parênteses aparecem como terminais consumidos; na AST, não há vestígio deles. Não é perda de informação: parênteses existem porque a escrita é linear — num texto de uma dimensão você precisa de marcadores para dizer o que agrupa com o quê. A árvore é bidimensional, e o agrupamento já está na posição do nó. Compare as ASTs de (2+3)*4 e 2+3*4: os formatos são diferentes, e é o formato que determina a ordem da conta.

Duas decisões que o enunciado não fixa — e podem ser perguntadas

Associatividade: 2**3**2 dá 64 aqui, porque o while acumula da esquerda para a direita, como os outros operadores. Matematicamente e em Python a potência é associativa à direita (daria 512). Para inverter, troca-se o while por recursão à direita: return result ** Parser.parse_factor().

Expoente negativo: 2 ** -3 é erro de sintaxe, porque o operando da direita é BASE e não FACTOR. É proposital: expoente negativo produziria fração e quebraria a garantia de resultado inteiro.

Um BinOp("+") não sabe se os filhos são números, contas gigantes ou — nos próximos roteiros — chamadas de função. Ele pede evaluate() e recebe um número. Nenhum nó olha o pai, nenhum olha os irmãos. É essa ignorância deliberada que permite acrescentar tipos de nó novos sem tocar nos existentes.

Fatorial   !

Enunciado: implementar o fatorial de um inteiro. O símbolo é !, o token se chama FACT, e ele é posicionado após o valor. A precedência é maior que a dos unários e menor que a dos parênteses. Fatorial de negativo não é aceito. Exemplo: -3! → -6.

Mesma precedência do ** — logo, mesma técnica

"Maior que os unários, menor que os parênteses" é exatamente a posição da potência do extra anterior. Então a solução é a mesma quebra do FACTOR em dois. A única diferença é que o operador vem depois do operando (pós-fixo), e não entre dois operandos.

FACTOR = ("+"|"-"), FACTOR | BASE, { "!" } ;
BASE   = NUMBER | "(", EXPRESSION, ")" ;
Nenhuma classe de nó nova

O fatorial é uma operação unária — um operador, um operando. Então ele reusa o UnOp com value = "!". A árvore de -3! fica com dois UnOp empilhados:

   UnOp('!')
      IntVal(3)

Esse é o teste real de que a arquitetura do Roteiro 4 aguentou crescer: três operadores novos nos extras (^, **, !) e zero classes novas.

A regra de ouro da precedência

Quanto mais fundo na cadeia de chamadas, mais forte o operador liga. Se o operador novo precisa ligar mais forte que X e mais fraco que Y, ele vai numa função chamada por X e que chama Y. Não existe tabela de prioridade — a hierarquia de chamadas é a tabela.

O investimento do Roteiro 4

Roteiro 8: os nós ganham um generate()

Irmão do evaluate(): percorre a mesma árvore com a mesma recursão, mas em vez de devolver um número, emite instruções de assembly. É nesse momento que o interpretador vira compilador de verdade — e nada disso seria possível se a conta tivesse sido feita durante a leitura, como era até o Roteiro 3.

Variáveis: o evaluate() passa a receber um argumento

Entram um nó Identifier, um Assignment e uma tabela de símbolos. O detalhe que importa é como a tabela chega aos nós: passada como argumento — evaluate(symbol_table) — e repassada aos filhos, nunca como global. Assim, quando surgirem funções com escopo próprio, basta passar outra tabela na chamada; a árvore não muda.

Potência e fatorial dividiram o parse_factor() em dois níveis para acomodar a precedência, e reusaram BinOp e UnOp tal como estavam. É o primeiro teste real de que a arquitetura aguenta crescer.
